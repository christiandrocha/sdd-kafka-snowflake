How the CDC pipeline
really works

A visual walkthrough of the 20-domain, 4-source CDC pipeline — from raw JSON to Grafana dashboards. What each layer does, the engineering decisions behind each choice, and why the stack is built the way it is.

01

The problem the pipeline solves

Problem 1

Food delivery data lives in 4 separate systems — Kafka, MongoDB, MySQL, MSSQL. Each has its own schema, encoding, and timestamp format. A single CDC connector cannot span all of them.

Problem 2

Timestamps arrive in two forms: integer epoch (1759687602, 17% of events) and scientific notation float (1.7596E12, 83%). Snowflake VARIANT stores both as-is — no automatic normalization.

Problem 3

The analytics team needs capture rates, revenue per restaurant per day, and driver performance — but the raw data arrives as CDC events in opaque VARIANT columns, not typed tables.

The answer: A unified PostgreSQL as CDC hub, Debezium + Kafka for streaming, Snowflake as the data warehouse, and a dbt Medallion (Bronze → Silver → Gold) for progressive transformation — orchestrated event-driven by Dagster.

03

Medallion Architecture — dbt

🥉
Bronze Layer
20 models · incremental + merge · unique_key via TABLE_METADATA
VARIANT → colunas tipadas Extrai campos com path notation: RECORD_CONTENT:event_id::VARCHAR. Cada model sabe quais campos extrair do seu domínio.
MERGE idempotente por PK unique_key vem de get_config_for(this.name) que lê CONFIG.TABLE_METADATA. Snowpipe retries não duplicam.
Filtro incremental por CreateTime RECORD_METADATA:CreateTime é o timestamp de ingestão do Snowpipe — monotonicamente crescente, imune a out-of-order do Kafka.
Dedup por ROW_NUMBER() Dentro do batch, CDC pode duplicar mensagens. ROW_NUMBER() PARTITION BY pk ORDER BY source_ts_ms DESC garante uma linha por PK antes do MERGE.
Normalização de timestamp ADR-13: CAST(PARSE_JSON(event):timestamp::FLOAT AS BIGINT) — o cast via FLOAT funciona para int (17%) e scientific notation (83%).
on_schema_change: sync_all_columns Quando Debezium detecta nova coluna no WAL, o schema Avro evolui no Registry. O bronze extrai a nova coluna e a tabela Snowflake acompanha automaticamente.
ref('bronze_*') · filtro incremental por source_ts_ms
🥈
Silver Layer
incremental (merge) + table (FULL OUTER JOIN) · lógica de negócio
silver_users — FULL OUTER JOIN users_mongo (contato) + users_mssql (perfil) unidos via CPF normalizado. materialized=table porque FULL OUTER JOIN é incompatível com incremental MERGE.
Normalização de CPF / CNPJ REGEXP_REPLACE(cpf, '[^0-9]', '') → 11 dígitos. Business key para joins cross-domain em gold sem depender de formatação.
Histórico de pagamentos silver_payment_events_history — um row por event_id, excluindo op='d'. Adiciona flags is_terminal, is_refund, event_sequence.
Estado atual de pagamento silver_payment_current_state — um row por payment_id. Último evento por timestamp. Merge por payment_id sobrescreve estado anterior.
silver_orders — join com restaurante Normaliza CPF/CNPJ dos business keys e faz join com bronze_restaurants para trazer nome do restaurante — evita repetir esse join em todos os models gold.
Testes singulares 7 arquivos SQL em tests/: CPF único em silver_users, histórico começa com 'created', integridade referencial entre current_state e history.
ref('silver_*') · full table refresh · joins cross-domain por CPF / CNPJ
🥇
Gold Layer
6 models · materialized=table · agregações analíticas cross-domain
gold_payment_funnel Conversão por estágio de lifecycle (7 estágios). COUNT(DISTINCT payment_id) por event_name + conversion_rate_pct via CROSS JOIN com entry count.
gold_payment_lifecycle Pivot de timestamps por payment_id — uma coluna por estágio. Computa duração em segundos entre transições. Merge por payment_id.
gold_revenue_per_restaurant Receita por restaurante por dia. Join silver_orders (CNPJ) com silver_order_items (subtotais). Uma row por restaurante × dia.
gold_driver_performance Performance por turno — ganhos, entregas, distância, shift_rating. Join driver_shifts com silver_orders (driver_id). Full refresh.
gold_user_behavior Comportamento por CPF unificado. Agrega pedidos (silver_orders), buscas (bronze_search_events), recomendações. Segmenta em engagement_tier: high / medium / low / inactive.
gold_payments_by_status Contagem de pagamentos por status atual. Uma row por status (7 possíveis). Incremental merge por current_status. Alimenta dashboard operacional.
Por que gold usa materialized=table? Agregações como COUNT(DISTINCT payment_id) e SUM(total_amount) precisam ser calculadas sobre o histórico completo. Incremental teria que reprocessar todos os dias afetados — mais complexo que um full refresh, que em 6 models de baixa cardinalidade é barato.
04

Engineering decisions (ADRs)

ADR-04

Unified PostgreSQL como hub de CDC

4 sistemas fonte (Kafka, MongoDB, MySQL, MSSQL)
→ 4 conectores Debezium separados
→ 4 configurações de auth, schema, monitoring
load_to_postgres.py carrega todos os domínios em um único PostgreSQL. Um conector Debezium lê o WAL de 20 tabelas. Monitoramento centralizado, um único slot de replicação.
ADR-13

Normalização de timestamp via FLOAT

83% dos eventos chegam como 1.7596E12 (scientific notation)
17% chegam como 1759687602 (integer)
→ VARIANT armazena ambos, mas ::BIGINT falha no float
CAST(PARSE_JSON(event):timestamp::FLOAT AS BIGINT) — cast via FLOAT primeiro converte scientific notation corretamente, depois trunca para BIGINT sem perda de precisão nos milissegundos.
ADR-14

order_items com conector separado

order_items = 110.001 registros (85% do volume total)
→ no mesmo buffer que outras 19 tabelas
→ buffer flush a cada 1.000 rec/60s = throttle de todos os tópicos
Conector sinkitems dedicado: buffer 5.000 rec / 120s / 25MB. As 19 tabelas restantes mantêm 1.000 rec / 60s sem competir com o volume de itens. Latência de outros domínios não é afetada.
ADR-06

Todas as tabelas usam upsert (MERGE)

Snowpipe retries reenviam a mesma mensagem
→ APPEND mode duplica dados em falhas de rede
→ eventos com op='r' (snapshot) reprocessados também duplicam
incremental_strategy: merge em todas as 20 tabelas bronze. O MERGE por unique_key garante idempotência — re-runs e retries não alteram o resultado final.
ADR-15

silver_users via FULL OUTER JOIN em CPF

users_mongo tem contato (email, telefone, endereço)
users_mssql tem perfil (nome, nascimento, profissão)
→ mesma pessoa em dois sistemas, sem FK explícita entre eles
CPF normalizado (11 dígitos, só números) é a business key. FULL OUTER JOIN garante que usuários presentes em apenas um sistema também aparecem. COALESCE(mongo, mssql) por campo. Coluna source indica a origem.
Macro

unique_key dinâmico via TABLE_METADATA

dbt precisa de unique_key para o MERGE
→ hardcodar em cada model = 20 arquivos a manter
→ mudança de estratégia CDC = 20 edições manuais
get_config_for(this.name) lê CONFIG.TABLE_METADATA uma vez por run (cache em contexto Jinja). Cada model recebe seu unique_key dinamicamente. Mudar a estratégia é um UPDATE no banco.
ADR-16

Resource Monitor para controle de custo

Trial de 14 dias Snowflake = 348 créditos
→ CDC contínuo pode esgotar créditos antes do fim do trial
→ sem monitor, o warehouse continua consumindo silenciosamente
cdc_trial_monitor com limite de 348 créditos, FREQUENCY=NEVER (acumula desde o início), aplicado via ALTER ACCOUNT. Suspende o warehouse ao atingir 100% do limite.
ADR-17

Time Travel por camada

BRONZE recebe dado do Kafka (retém 7d)
SILVER/GOLD são derivados — erros de transformação precisam ser revertidos
→ Time Travel uniforme não reflete o ciclo de cada camada
BRONZE = 1 dia (Kafka retém 7d — dado bruto pode ser reprocessado da fonte). SILVER e GOLD = 7 dias (transformações são caras de refazer — Time Travel mais longo protege contra erros de modelo).
05

Dagster — Orquestração event-driven

Dagster não usa schedules (cron). O pipeline dispara quando novo dado chega — o bronze_new_data_sensor detecta avanço no MAX(RECORD_METADATA:CreateTime) das 20 tabelas bronze. Se não há dado novo, o sensor retorna SkipReason — nenhum run é disparado, nenhum crédito é consumido.

▣ sensors.py
  • bronze_new_data_sensor interval: 60s · job: cdc_pipeline_job lê MAX(CreateTime) de 20 tabelas · cursor persiste no SQLite · run_key idempotente
  • registry_new_subject_sensor interval: 300s · job: sync_metadata_job GET /subjects no Registry · diff com TABLE_METADATA · dispara sync se há tabela nova
▣ assets.py
  • cdc_dbt_assets @dbt_assets · manifest.json · DAG do dbt visível na UI dbt run bronze silver gold → dbt test bronze silver gold
  • log_processing_results @asset · deps=[cdc_dbt_assets] lê run_results.json · COUNT(*) por tabela · INSERT PROCESSING_LOG
▣ jobs.py
  • cdc_pipeline_job define_asset_job · AssetSelection.all() executa cdc_dbt_assets + log_processing_results em sequência
  • sync_metadata_job @job com op run_sync_metadata subprocess.run(sync_metadata.py) · INSERT/UPDATE TABLE_METADATA + METADATA_HISTORY
▣ resources.py
  • DbtCliResource project_dir: /opt/dagster/dbt · target: dev/prod via env_var
  • SnowflakeResource auth: private_key_path (PKCS8) RetryPolicy: max_retries=3 · delay=30s · EXPONENTIAL backoff
-- sensors.py — lógica central do bronze_new_data_sensor
last_cursor = int(context.cursor or "0")
current_max = max(
  _get_max_create_time(conn, table)  -- SELECT MAX(RECORD_METADATA:CreateTime::BIGINT)
  for table in BRONZE_TABLES        -- 20 tabelas
)

if current_max <= last_cursor:
  return SensorResult(skip_reason=SkipReason(...)) -- sem run

return SensorResult(
  run_requests=[RunRequest(run_key=str(current_max))], -- idempotente
  cursor=str(current_max)                          -- avança o cursor
)

CI/CD Pipeline

CI — todo pull request para main
✓
pre-commit hooks — detect-secrets, check-json, check-yaml, trailing-whitespace (roda local antes do push)
▣
dbt compile --profiles-dir .ci/profiles — valida sintaxe Jinja, ref(), source(), macros. Sem conexão ao Snowflake (credenciais dummy).
▣
lint connector JSONs — python -m json.tool para debezium.json, snowflake_sink.json, snowflake_sink_items.json
🛡
.env guard — git diff --name-only | grep ^\.env$ → exit 1 se encontrar. Bloqueia merge com credenciais.
→
CI success
merge to main
CD — merge to main
🔑
GitHub Secrets → env vars — SNOWFLAKE_PRIVATE_KEY, SNOWFLAKE_URL, POSTGRES_USER, etc. Nunca em disco.
↑
register_connectors.sh --env prod — envsubst substitui ${VARS} nos JSONs · POST /connectors · HTTP 409 = idempotente · verifica state=RUNNING
▶
Dagster restart — SSH ou deploy API. Daemon recarrega o workspace e os sensores voltam ativos com cursores preservados no SQLite.
workflow_run trigger — CD nunca executa sem CI verde
-- register_connectors.sh — envsubst garante que credenciais nunca vão a disco
RESOLVED=$(envsubst < connectors/debezium.json)    -- substitui ${SNOWFLAKE_URL} etc.
HTTP=$(echo "$RESOLVED" | curl -sf -w "%{http_code}" \
  -X POST "${CONNECT_URL}/connectors" \
  -H "Content-Type: application/json" -d @-)

case "$HTTP" in
  201) echo "criado"        ;; -- primeira vez
  409) echo "já existe"   ;;  -- idempotente: deploy repetido não falha
  *  ) exit 1           ;;  -- qualquer outro código → falha o pipeline
esac
